Fix the empty `payment_handlers` regression on checkout session responses. PR #8 ("pass cart.total in major units") changed amount construction from `(totalMinor / 100).toString()` to `String(totalMajor)`. The previous division accidentally triggered Medusa v2 BigNumber's `Symbol.toPrimitive` with hint `"number"` (returning the plain `.numeric` value), so the final `.toString()` ran on a regular JS number and produced a clean decimal string. The new direct `String()` triggers `Symbol.toPrimitive` with hint `"string"`, which returns the underlying bignumber.js raw value at 20-digit precision — e.g. `"34"` becomes `"34.000000000000000000"`. Prism's `/payment-requirements` endpoint rejects that format, the call throws, `Promise.allSettled` swallows the rejection, the adapter returns `null`, no metadata is written to the cart, and the checkout session response renders with `payment_handlers: {}` — agents see `ready_for_complete` with no way to pay.

The fix coerces `cart.total` to a plain number via `Number()` (which triggers `Symbol.toPrimitive` with hint `"number"` → returns `BigNumber.numeric`) before stringifying, so the amount sent to Prism is `"34"` or `"17.5"` as expected. Adds two regression tests on the existing amount-unit suite that exercise the actual Medusa BigNumber `Symbol.toPrimitive` contract — the original tests passed plain JS numbers and therefore couldn't catch this class of bug.
